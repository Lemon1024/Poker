## 1 任务目标与执行方式

开发 Android/iOS 手机 App，离线完成两项精确分析，并保留和实施真正的单挑河牌 GTO 求解：

1. 翻前双方具体底牌固定的 all-in 胜平负与底池权益。
2. 已知自己的两张底牌和 3/4/5 张公共牌，分析每个合法对手组合的当前牌力关系、最终胜平负概率和权益。
3. 给定双方完整范围、河牌、底池、筹码和有限下注树，计算平均策略、行动 EV 与可利用度。

这是实施任务。Codex 应创建和修改源码、执行必要测试、修复问题、生成可完成的构建物。普通实现决策按本规格自主选择，通过一个关卡后继续下一阶段；不要重复把已经确定的技术方向变成澄清问题。

本执行包不是现成 App。fixtures 是参考测试数据，不能替代生产计算。平台构建和运行结论必须由后续执行产生的证据支持。

## 2 功能规格

### 2.1 翻前固定组合

输入自己的两张具体牌、对手两张具体牌，公共牌为空。排除四张底牌后枚举剩余48张牌的所有五张公共牌：

C(48,5) = 1,712,304。

对每个牌面比较双方七张牌的最佳五张牌，累计自己的 wins、ties、losses。对手统计由同一结果交换得到；不能再次运行一个可能采用不同分布的独立计算。

输出：
- 整数 wins、ties、losses、total；
- win_probability、tie_probability、loss_probability，取值0到1；
- equity = (wins + ties/2) / total；
- method=exact、status=completed、request_id、engine_version；
- 计算时间等性能元数据可存于独立报告，遵守输出schema。

具体花色是输入的一部分。“AA 对 KK”的类别均值不能替代 AsAh 对 KsKh。

### 2.2 牌面组合分析

输入自己的两张牌与 3、4、5 张公共牌。默认枚举全部合法对手两张组合，也支持具体组合及0到1权重。

每个结果行记录：
- 对手具体组合；
- current_relation：winning、tied、losing，以自己的视角表示；
- 所有合法未来公共牌下的 wins、ties、losses、total；
- 对应概率与 equity；
- 用户输入的范围权重。

current_relation 只依据当前已有牌的最佳五张牌。翻前不定义这个字段，不能拿两张底牌直接评估当前五张牌型。

翻牌和转牌的“当前领先”不代表最终必赢。筛选“最终权益超过50%”使用 equity，不使用当前关系或独赢率冒充。

河牌时，每个确定对手组合的最终结果是赢、平、输之一。平局对应独赢0%、平局100%、权益50%。

### 2.3 合法组合与状态规模

以下假设标准52张牌，无额外已知死牌：

| 模式 | 对手组合数 | 每个对手的补牌数 | 总终局 |
| --- | ---: | ---: | ---: |
| 翻前双方固定 | 1 | 1,712,304 | 1,712,304 |
| 翻牌组合分析 | 1,081 | 990 | 1,070,190 |
| 转牌组合分析 | 1,035 | 44 | 45,540 |
| 河牌组合分析 | 990 | 1 | 990 |

这些值用于完整均匀范围。自定义范围只评估过滤后权重大于0的合法组合；available_legal_combo_count 仍表示牌面允许的完整数量，evaluated_combo_count 表示实际计算的组合数量。

翻前只固定自己手牌、对全部未知对手分析，是约20.98亿终局的不同需求，当前模式不得悄悄退化成该计算。多人、边池、死牌另开带版本号的需求。

### 2.4 范围规则

- 默认 uniform：所有合法具体两张组合等概率。
- weighted：用户提供具体组合，权重范围[0,1]。
- 权重是相对频率，不要求输入和为1。
- 先拒绝重复组合，组合内部牌序不影响唯一性。
- 先排除被自己手牌或公共牌阻挡的组合，再排除零权重组合；记录两类排除数量。
- 过滤后无有效组合，返回 EMPTY_EFFECTIVE_RANGE，不返回0%胜率。
- 负数、非有限数、超过1的权重属于非法请求，返回 INVALID_REQUEST。
- 权益汇总为 sum(weight * equity) / sum(weight)，胜平负概率同理。
- 169格矩阵仅是展示层。不得对169个类别直接等权平均。
- 用户改变范围权重时，可复用相同牌面已完成的逐组合精确结果，重新汇总；只能复用确实存在的行。

### 2.5 结果解释

结果始终标明“针对当前范围”。默认范围文字为“所有合法对手组合等概率”。组合计数占比不代表真实对手必然按该分布持牌。

在结果详情展示双方最佳五张牌和简短原因，例如“一对Q，A踢脚大于K”。解释由评估器输出的牌型和踢脚生成，不调用语言模型猜测结果。

## 3 手机界面

### 3.1 全下对比

依次展示双方手牌、计算按钮、权益对比条、胜平负明细、交换与保存。支持：
- 已用牌禁选；
- 重复输入错误定位；
- 一键交换；
- 计算进度；
- 取消任务；
- 相同配置缓存命中。

### 3.2 组合分析

顶部固定显示自己手牌、公共牌、街道与范围说明。

汇总区显示合法与实际评估组合数量、当前领先/相同/落后计数，以及完成后的总体概率。

列表显示具体对手牌、当前关系、最终权益；详情展开整数计数、胜平负、最佳五张牌。

筛选包括当前关系、最终权益阈值、手牌类别、点数、自定义范围。当前关系与最终权益是独立筛选维度。对于浮点比较，用定义明确的阈值和显示规则；精确50%可以直接比较 2*wins+ties 与 total。

矩阵只作概览，点击后用放大面板编辑具体组合和权重。颜色同时配文字或图标。组合列表使用懒构建，支持窄屏和文字缩放。

### 3.3 历史与缓存

保存输入、范围、模式、引擎版本、创建时间、备注与已完成结果。缓存只存完成的精确结果。

缓存键包含模式、规范化牌张、公共牌、具体组合及权重、引擎版本和收益规则。request_id 不属于复用结果的数学配置。命中缓存后按当前request_id包装响应，不能回传旧任务标识。

未来GTO缓存还必须加入双方完整范围、底池、筹码、下注树与求解参数。

### 3.4 GTO界面

M3完成后开放真实策略页面，输入双方范围、河牌、底池、筹码与允许动作，展示行动频率、行动EV和测得的求解误差。

没有真实引擎的界面不得以演示数字伪装成功结果；开发中的占位组件不能计入交付完成。

## 4 计算实现

### 4.1 牌与评估器

- 内部建议 card_id = rank_index * 4 + suit_index，rank_index按23456789TJQKA，suit_index按cdhs。
- 两张组合按card_id排序；保存组合唯一ID或确定性索引。
- 若第三方评估器编码不同，单独写适配层并测试全52张映射，不能直接传错编码。
- 64位掩码检查牌张冲突。
- 统计计数采用uint64_t，概率采用double。
- 生产评估器可用锁定版本的PH Evaluator或通过同等验证的自研实现。
- 独立参考评估器采用五张牌排名并枚举五选/六选五/七选五，不能复用生产核心的排名函数。

必要牌型边界：A2345顺子、顺子与同花优先级、同花踢脚、双三条取葫芦、三对取最高两对、公共牌直接构成最佳牌、四条踢脚、平局。

### 4.2 枚举

翻前固定双方手牌：枚举剩余48张的五张无序组合。

翻后组合分析：可以按对手组合遍历补牌，也可以按最终公共牌遍历合法对手组合。后一种方式可减少同一最终牌面下重复评估自己的手牌。两种遍历应在小规模用例上互相验证。

对每个合法对手，翻牌分母990，转牌44，河牌1。按整数计数计算概率，展示层再转成百分比。

这里计算的是发完牌后的摊牌权益，未来发牌可以按无序补牌枚举。扩展完整翻牌GTO策略树时，转牌与河牌之间有行动，不能直接沿用无序补牌合并。

### 4.3 进度与取消

确定性枚举的前缀通常不是均匀随机样本，未完成时不能把当前计数除以已完成次数后显示为总体胜率。

M1/M2默认：
- 运行中只发送进度、任务状态和错误；
- 任务完成才发送概率与完整结果；
- 若未来增加快速估计，必须有独立随机抽样模式和明确误差标识，不能复用枚举前缀。

默认采用后台长生命周期isolate拥有一个原生任务，循环调用有工作量上限的step。每批结束让出事件队列处理取消与新任务。详细ABI和所有权见docs/API_AND_FFI.md。

## 5 验收金标

### 5.1 翻前固定组合

输入 Hero=[As,Ah]，Villain=[Ks,Kh]：

| 字段 | 精确整数 |
| --- | ---: |
| wins | 1,410,336 |
| ties | 9,308 |
| losses | 292,660 |
| total | 1,712,304 |

Hero equity = (2*1,410,336 + 9,308) / (2*1,712,304)，约82.636611%。

不能只核对显示为82.64%，必须比较整数计数。花色不同不是同一金标。

### 5.2 河牌全组合

输入 Hero=[As,Qs]，Board=[Qd,8s,2s,7h,3c]，uniform：

| 字段 | 精确整数 |
| --- | ---: |
| available_legal_combo_count | 990 |
| evaluated_combo_count | 990 |
| Hero赢的组合数 | 884 |
| 平局组合数 | 6 |
| Hero输的组合数 | 100 |

总体权益 = 887/990，约89.595960%。

selected rows：
- 对 Qc Kd：自己赢。
- 对 Ac Kh：自己赢。
- 对 Ac Qh：平局。
- 对 7d 7c：自己输。

输的组合按最终牌型：三条13、两对78、比QQ大的对子9。fixture摘要不是完整990行响应；程序必须自己生成全部行。

### 5.3 不变量

- 单行 wins+ties+losses=total。
- 单行三种概率之和为1，权益公式成立。
- 单挑双方权益和为1。
- 全范围的合法组合数符合第2.3节。
- weighted汇总等于逐行概率加权结果，不能伪造“加权整数胜场”。
- 全局花色一致置换后相应结果相同。
- 交换双方底牌后胜负交换、平局不变。
- 同一输入缓存和新计算结果一致。
- 当前关系与最终权益分别保存。
- 旧请求、取消请求和失败请求不得更新当前完成结果。

### P1 牌力与翻前

实现独立CMake库、CLI和测试入口。命令行接受schema定义的请求JSON，输出完成结果或结构化错误。

完成独立参考五张牌评估器与随机/边界差分。完成翻前精确枚举。至少在本阶段结束前完整运行一次1,712,304终局金标。

### P2 翻后与范围

实现完整对手组合生成、当前关系、补牌枚举、weighted聚合和排序。验证河牌完整990行、翻牌/转牌总规模以及范围过滤边界。

不要把数学上不可能的重复牌、非法board长度或空范围交给界面静默修正。

### P3 原生接口与任务生命周期

为C++添加稳定C ABI并生成/维护Dart绑定。主机原生库、Android和iOS编译分别处理；按实际SDK支持的官方模板集成。

所有原生内存配套释放。C++异常转结构化错误。step有上限；取消、退出、重算、缓存命中都使用一致状态机。验证多轮开始/取消/销毁，不以“Future取消”代替实际停止。

界面在接口稳定后可以与引擎并行开发。用于布局的fixture数据必须局限在测试/预览环境，生产流程只用真实引擎。

### P4 手机流程与平台构建

接入真实计算；完成选牌、范围、列表、详情、筛选、历史与缓存。做窄屏、文字缩放、加载、空结果、错误与取消状态验证。

Android优先生成可安装开发APK并在可用设备或模拟器运行。iOS在macOS/Xcode可用时编译与运行模拟器；签名和真机安装仅在所需条件实际具备时执行。

记录每个平台的compile/emulator/device状态。没有设备时，不声称已真机验证。性能使用profile/release等适当构建，记录设备和输入规模，不从桌面测试推断手机秒数。

### P5 真正GTO

先用小型扑克检查CFR、平均策略和独立最佳响应，再进入受限单挑河牌。严格执行docs/GTO_RIVER_SPEC.md。在fixtures/gto_river_small_v1.json固定基准上由独立BR测得exploitability/root_pot≤0.001，才可通过河牌内核关卡；只有误差输出或超时不算通过。

不能用权益大于50%的规则代替GTO行动。固定范围下的河牌均衡不等于完整德州扑克全局解。

### P6 交付

整理源码、依赖锁、第三方许可、应用构建、真实测试日志、设备截图（若实际取得）、性能报告和使用说明。

T11接入GTO后，T12必须对受影响的平台重新构建并做必要冒烟验证，记录源码commit或其他可复现的源码指纹。旧APK若只包含M2，就明确标为M2，不得作为包含M3的最终版本。

报告必须按模块分别说明M1/M2/M3，并按平台分别说明编译、模拟器和真机。若存在阻碍，列出已完成部分、缺失条件和最小恢复步骤。

## 7 并行协作

仅在T01契约冻结后并行：

- 原生计算代理：native/、CLI、生产评估与枚举。
- 移动界面代理：Flutter视图、状态、范围与历史。
- 验证代理：独立参考、golden、性质测试与报告。
- 主代理：契约、FFI集成、冲突解决、平台构建与关卡验收。

共享schema和ABI由主代理维护；更改先通知依赖方。给每个代理明确文件范围。没有多代理工具时按依赖顺序执行。

## 8 进度记录与阻碍处理

创建并持续维护：
- reports/STATUS.md：任务状态、完成证据、下一项；
- reports/ENVIRONMENT.md：实际工具链；
- reports/VALIDATION.md：运行命令、测试结果、已知限制；
- reports/PERFORMANCE.csv：设备、构建模式、场景、规模、耗时、峰值内存；
- reports/DELIVERY.md：可交付文件和未验证项。

状态使用planned/in_progress/passed/blocked，不把跳过记成passed。

遇到平台缺失时继续不受影响的工作。只有确实需要用户信息、外部权限或改变关键规格时再提问。常规目录名、配色、局部依赖选择、实现细节按默认方案处理并记录。

## 9 最终验收定义

完整交付应满足：
1. 用户可以输入具体底牌得到精确翻前all-in结果。
2. 用户可以输入公牌得到所有合法对手组合的真实逐行结果。
3. 范围筛选与聚合正确，当前领先与最终权益不混用。
4. 任务取消、错误、改牌和缓存状态正确。
5. 支持的平台有各自真实构建证据，设备运行情况如实记录。
6. 真正GTO模块有平均策略、动作EV、独立BR和明确模型内误差。
7. 源码、锁定依赖、测试、构建步骤和使用说明完整。

本方案不要求在没有工具链或设备时虚构以上证据。最终报告要呈现已经实际达到的等级，同时完成所有仍可推进的工作。
